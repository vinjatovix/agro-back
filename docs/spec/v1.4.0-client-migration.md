# CLIENT MIGRATION GUIDE: v1.3.0 → v1.4.0

Audience: front-end and any other API client. Backend changelog: [v1.4.0.md §8](v1.4.0.md#8-changelog).

---

## 1. WHEN EACH CHANGE TAKES EFFECT

- **Every change below takes effect at the same moment: when the backend v1.4.0 is deployed.** There is no feature flag and no transition window.
- v1.3.0 (what is running today) has none of them.
- Two changes break a client immediately on deploy (§3.1 and §3.2). The rest only change status codes that the client must handle.

### Recommended rollout order

1. **Front ships a forward-compatible build first** (checklist in §4). It works against v1.3.0 and v1.4.0 alike.
2. **Backend deploys v1.4.0** only after that build is in production.

If the backend is deployed first, **every `PATCH` and `DELETE` on beds, plants and families fails with `428`** until the front catches up.

## 3. DETAILS

### 3.1 `If-Match` is required on writes — breaks immediately

Each single-resource response now carries the version the client must send back:

```http
GET /api/v1/beds/0199...        →  200 OK
                                    ETag: "3"
                                    { ..., "version": 3 }

PATCH /api/v1/beds/0199...
If-Match: "3"                   →  200 OK
                                    ETag: "4"
```

- `ETag` comes on single-resource `GET`, `POST` and `PATCH` of beds, plants and families. It is always equal to the body's `version`, so either can be used. Lists, `204` and error responses have no `ETag`.
- The value is a quoted integer: `If-Match: "3"`. The quotes are part of the value.
- Responses:
  - no header, empty or `*` → `428 Precondition Required`;
  - malformed (`W/"3"`, `"3", "4"`, `3` without quotes, negative, non-numeric) → `400` with `errors["if-match"]`;
  - outdated → `412` (see §3.3).
- The header is checked right after authentication and role checks: `401`/`403` still come first, and `428`/`400` come before body validation and before checking that the resource exists.
- Browsers: CORS exposes `ETag` to allowed origins and accepts `If-Match` in preflights, so `response.headers.get('ETag')` works cross-origin.
- After a successful `PATCH`, use the new `ETag` for the next write. A `DELETE` needs the current version too.

### 3.2 Do not send `version` in request bodies — breaks immediately if echoed

- Bed, plant and family responses now include a read-only `version` (integer, starts at `0`).
- Request bodies reject unknown fields, and `version` is not writable: a body containing `version` returns `400`.
- This only breaks clients that build `POST`/`PATCH` bodies by spreading a previously received object (`{ ...bed, name }`). Send only the fields being changed.

### 3.3 Outdated versions return `412`

- If the resource changed since the client read it, the write is rejected with `412` and nothing is modified. Body: `{ "message": "..." }`, no `ETag`.
- Suggested handling: reload the resource with `GET`, show the user the current state, and let them re-apply the change. Do not retry blindly with the new version; that would overwrite the other person's change, which is exactly what this prevents.
- Precedence when several things are wrong: `404` wins over `412` (a missing, deleted or foreign resource never reveals its version), and `412` wins over `409` (e.g. deleting a bed that has plants with an outdated version returns `412`).
- `409` still exists, only for business rules: duplicates, or deleting a bed that has plants.

### 3.4 Another user's bed returns `404` instead of `403`

- `GET`, `PATCH` and `DELETE` on a bed owned by someone else now return `404`, as if it did not exist, so bed ids cannot be probed.
- Any UI that shows "you do not have access" on `403` for beds should handle `404` the same way.

### 3.5 A repeated `DELETE` returns `404`

- Deleting a bed or plant that is already deleted returns `404` instead of `204`.
- The server state is identical either way, so the operation is still safe to repeat. Clients that retry deletes (e.g. after a timeout) should treat `404` as success.

## 4. FORWARD-COMPATIBLE CHECKLIST (works against v1.3.0 and v1.4.0)

Ship this before the backend deploy:

- [ ] Store the `ETag` (or `version`) of each bed, plant and family read or written.
- [ ] Send `If-Match` on `PATCH`/`DELETE` of beds, plants and families **whenever an `ETag` is known**. v1.3.0 ignores the header and returns no `ETag`, so nothing is sent there and nothing breaks.
- [ ] On `428` (e.g. data loaded before the deploy, without an `ETag`): reload the resource, then let the user retry.
- [ ] Handle `412` as described in §3.3.
- [ ] Never include `version` (or other read-only fields) in request bodies.
- [ ] Beds: treat `403` and `404` the same.
- [ ] `DELETE`: treat `404` as "already deleted".

---

## 5. UPCOMING (NOT IN v1.4.0)

- The planned layout save endpoint, `PUT /api/v1/beds/{id}/layout`, will also require `If-Match` with the bed version, with the same responses as §3.1 and §3.3 (`428`, `400`, `412`), and will return the new `ETag`. Build the layout editor on the same version handling from the start. The dry-run `POST /api/v1/beds/{id}/layout/validate` writes nothing and needs no `If-Match`.
- It takes effect when that endpoint ships ([roadmap Iteration 67](../roadmap.md#iteration-67-implement-transactional-batch-save-layout-endpoint)); there is no date yet.

---

## 6. NON-BREAKING ADDITIONS

- `PATCH /families/{idOrSlug}` accepts the slug as well as the id (the id keeps working).
- `version` in bed, plant and family responses (read-only).
- A single-resource `GET` sent with a matching `If-None-Match` returns `304` with no body. Browsers handle this transparently through their HTTP cache; clients that send `If-None-Match` themselves must handle `304`.
